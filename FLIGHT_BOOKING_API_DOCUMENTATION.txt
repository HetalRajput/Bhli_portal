FTD FLIGHT BOOKING API DOCUMENTATION
====================================

Base URL
--------
Local: http://127.0.0.1:8000
API prefix: /api

Provider Mode
-------------
The backend uses FTD credentials from .env when available.
If credentials are missing or FTD_USE_MOCK=True, the API returns mock success responses for local testing.

FTD authentication flow:
1. Backend calls GET /postCreateToken using agentid, username, password, mode, and apikey.
2. FTD returns token in response field data.
3. Backend caches this token until end of day because FTD allows limited daily token generation.
4. Search, fare details, price verify, and seats use the generated token as x-api-key.
5. Fare rules also use the generated token as x-api-key.
6. Booking/cancel/status use the original FTD API key as apikey where required by the FTD spec.
7. Booking clientID is generated uniquely by backend for every booking request.

Required optional .env keys:
FTD_BASE_URL=http://13.200.42.214/book/api
FTD_USERNAME=
FTD_PASSWORD=
FTD_AGENT_ID=
FTD_API_KEY=
FTD_MODE=0
FTD_CLIENT_ID=BHLI
FTD_TIMEOUT=60
FTD_USE_MOCK=False

Note:
- FTD_CLIENT_ID is treated as a prefix, not a fixed booking id.
- Example generated clientID: BHLI-125-141500-A1B2C3
- Keep it blank to use default prefix BHLI.

Logs
----
Every FTD provider call writes:
1. Database log: bookings_ftdflightproviderlog
2. File log: logs/flight/<timestamp>_<action>.json


FRONTEND IMPLEMENTATION FLOW
============================

Use this order on the website:

Step 1. User opens flight booking page
--------------------------------------
Frontend shows a flight search form.

Required form fields:
- trip type: one way or round trip
- service type: domestic or international
- departure city airport code
- arrival city airport code
- departure date
- return date, only for round trip
- adults
- children
- infants
- cabin

Frontend does not need to call the FTD token API.
Backend handles FTD token generation and caching automatically.


Step 2. Search flights
----------------------
Call:
POST /api/bookings/flight/search/

Payload:
{
  "trip_type": 0,
  "service_type": 1,
  "dep_city": "DEL",
  "arr_city": "BOM",
  "on_date": "2026-08-20",
  "re_date": null,
  "adults": 1,
  "children": 0,
  "infants": 0,
  "cabin": "E",
  "fare_type": "A"
}

Response to use:
{
  "success": true,
  "data": {
    "search_session": 9,
    "ref_id": "FTD19Z9V1C4RHKRK",
    "search_flight_id": "168177",
    "provider_response": {}
  }
}

Frontend should:
- Show flight list from data.provider_response.results.
- Store search_session.
- Store ref_id.
- Store selected flight's search_flight_id.

Important:
- search_flight_id is only for fare-details.
- Do not use search_flight_id for price verify or final booking.


Step 3. User selects one flight / fare
--------------------------------------
Call fare-details when the user clicks View Fare, Select Flight, or Continue.

Call:
POST /api/bookings/flight/fare-details/

Payload:
{
  "ref_id": "FTD19Z9V1C4RHKRK",
  "flight_id": "168177"
}

Response to use:
{
  "success": true,
  "message": "Fare details fetched successfully.",
  "ref_id": "FTD19Z9V1C4RHKRK",
  "search_flight_id": "168177",
  "booking_flight_id": "168181",
  "data": {}
}

Frontend should:
- Show fare details from data.
- Store booking_flight_id.

Very important:
- Use booking_flight_id for price verify.
- Use booking_flight_id for fare rules.
- Use booking_flight_id for final booking.


Step 4. Verify latest price
---------------------------
Call this before showing the final review/payment/submit screen.

Call:
POST /api/bookings/flight/price-verify/

Payload:
{
  "ref_id": "FTD19Z9V1C4RHKRK",
  "flight_id": "168181"
}

Response:
{
  "success": true,
  "message": "Flight price verified successfully.",
  "data": {
    "success": 1,
    "errorDesc": "",
    "result": {}
  }
}

Frontend should:
- If success is true, show final fare amount from data.result.
- If price changed, show updated fare before user submits booking.
- If success is false, ask user to search/select flight again.


Step 5. Fetch fare rules, optional but recommended
--------------------------------------------------
Call:
POST /api/bookings/flight/fare-rules/

Payload:
{
  "ref_id": "FTD19Z9V1C4RHKRK",
  "flight_id": "168181"
}

Response:
{
  "success": true,
  "message": "Fare rules fetched successfully.",
  "data": {
    "farerule": {},
    "policy": {}
  }
}

Frontend should show:
- cancellation policy
- reissue policy
- no-show policy
- baggage/seat remarks, if available

Frontend asks passenger details.

Passenger fields:
{
  "title": "Mr",
  "first_name": "Rahul",
  "last_name": "Sharma",
  "passenger_type": "A",

Frontend Field Mapping
----------------------
Search response:
- data.search_session -> send in final booking payload
- data.ref_id -> send to fare-details, price-verify, fare-rules, booking
- selected flight flightID from provider_response -> send to fare-details as flight_id

Fare-details response:
- booking_flight_id -> send to price-verify, fare-rules, booking as flight_id

Booking response:
- data.id -> local FTDFlightBooking id
- data.booking -> common BookingRequest id
- data.pnr -> show PNR to user
- data.ticket_number -> show ticket/reference if available
- data.status -> local flight booking status
- data.provider_status -> FTD status


Common Frontend Rules
---------------------
- Always call fare-details after search and before price-verify.
- Always use booking_flight_id after fare-details.
- Do not generate or pass clientID from frontend.
- Do not call FTD API directly from frontend.
- Do not expose FTD API key or token in frontend.
- If any API returns success=false, show the message and ask user to retry/search again.
- Booking API requires login. Search/fare/price/fare-rules can be used without login.
